# Android 更新与发布

正式更新的目标仓库是公开仓库 `vilab-orulink/Vinote-app-public`。调试包和正式包具有不同的应用标识与签名，不应互相覆盖；调试包的运行和热刷新不代表正式包 OTA 已验收。

## 更新流程

1. 查询该仓库最新的正式 Release；草稿和预发布版本不进入正式更新。
2. 检查版本号、APK 下载地址、大小以及 Release 资产的 SHA-256 摘要；校验信息不完整时只提供发布页面，不自动安装。
3. 下载到应用私有缓存并核对大小和 SHA-256；用户可以取消。下载完成不代表安装完成。
4. 安装前检查 APK 的应用标识、递增的 Android `versionCode` 和与当前应用一致的签名证书。Android 的安装权限与最终安装由用户在系统界面确认。

## 正式版发布要求

- 确认 `package.json`、Android `versionName`、`versionCode` 与发布标签一致；每个正式更新的 `versionCode` 必须递增。
- 使用现有正式签名密钥构建；妥善保管密钥及备份，不提交到 Git，也不将密钥写入安装包或发布说明。密钥不一致的 APK 无法覆盖更新。
- 为合并后的代码创建对应版本标签；在公开仓库创建同版本的正式 Release，上传正式签名 APK，并写明相对上一版本的改动和已知限制。
- 核对 Release 资产的下载地址和 SHA-256 摘要可公开读取。保留原始构建产物与签名校验记录。
- 正式 Release 发布并核验后，同步更新公开仓库 `main/latest.json`，包含已发布版本、Release 页面、APK 地址、大小和 GitHub 返回的 SHA-256。GitHub API 限流时客户端使用该清单，APK 仍须经过摘要、包名、版本和签名验证。
- 在真实设备从上一正式版本执行检查、下载、校验和系统安装，重启后核对版本及原有账号和内容；需要同时验证拒绝错误包名、旧版本及错误签名。

当前开发代码已将更新入口接入设置页，并包含下载校验、安装器入口和对应离线测试。0.1.6 在部分网络的 GitHub 下载入口超时，已标为预发布；真机已从 0.1.7 通过应用内下载和系统安装器升级到公开发布的 0.1.8，版本号核验为 13。升级后的账号及会议数据仍需单独核对。

旧正式包使用不同签名，Android 不允许新包直接覆盖旧包。安装新签名基线前应先保留旧版数据；后续发布必须使用与新基线相同的密钥。密钥及密码的备份应单独安全保管，避免仅依赖当前 Windows 用户的加密配置。
